# 现代化重构总览与路线图

> 文档口径：本文是本次现代化重构的范围、验收与后续决策入口。玩法数值以[玩法设计](玩法设计.md)为准，界面以[视觉与交互设计](视觉与交互设计.md)为准，代码接口以[开发指南](开发指南.md)为准。
>
> 状态词只有两种：**本次交付**指本版本代码中应可直接操作的规则或界面；**候选（未实现）**指后续评审项，不是隐藏开关，也不保证排期。历史评审里的“建议”同样不代表已上线功能。

## 1. 重构目标

把《使魔卡牌对战》从“功能很多、信息堆叠的卡牌实验页”重构为“30 秒能完成首轮、每轮有明确战术选择、战斗过程可读、桌面与窄屏都能操作”的现代网页卡牌游戏。

本次坚持三条产品主线：

1. **构筑更清楚**：卡库、筛选、牌组各就其位；玩家随时知道缺多少张、为何不能开战、下一步该做什么。
2. **战斗更有代理感**：保留自动战斗与三排阵型，在每轮部署末加入一次轻量战术指令，不把游戏改成高频微操。
3. **远征更有构筑感**：在既有分支地图、抓牌、篝火和商店之外加入可叠加出流派差异的遗物，精英/Boss 奖励成为构筑节点。

非目标：不重写为引擎框架、不引入构建链、不更换卡牌数据源、不推倒既有三排/士气/反击规则、不添加账号体系或付费系统。

## 2. 现状问题与设计回应

| 基线问题 | 对玩家的影响 | 本次回应 | 可观察结果 |
| --- | --- | --- | --- |

| 闯关奖励主要堆牌，流派成长有限 | 精英与 Boss 只是更高数值门槛 | 至少 6 种有真实引擎效果的遗物，精英/Boss 后三选一 | 同一阵营可形成不同战术/士气/资源路线；刷新后遗物仍在 |

## 3. 本次交付清单

### 3.1 玩法与系统

- 每轮每方最多一种战术指令，开战前可更改，默认不选择：
  - `assault` **猛攻**：己方单位本轮战斗攻击 +1。
  - `guard` **坚守**：己方单位本轮战斗有效护甲 +1。
  - `rally` **集结**：己方单位本轮战斗士气 +2。
- 战术只持续当轮，不写入卡牌基础值，不跨轮残留；人机、热座、联机和 AI 使用同一规则入口。
- AI 根据公开战况选择指令，不读取玩家私有手牌，也不通过改状态作弊。
- 战斗表现速度支持 `1x / 2x / 4x`，默认 `1x`。速度只改变等待/表现，不改变行动顺序、随机调用顺序或战斗结果。
- 每轮保留结构化 `state.roundSummary`，至少覆盖双方英雄受伤、单位阵亡、触发指令与关键结果；详细战斗日志继续保留。结构化字段齐全不代表 UI 全部直接可见：紧凑摘要只显示双方英雄伤害、阵亡数和结果，战术看当前徽标，名单与关键结果看详细日志。
- Roguelike 至少 6 种有实际效果的遗物；精英与 Boss 胜利后提供遗物三选一；当前遗物可查看，远征存档兼容没有遗物字段的旧档。

### 3.2 视觉与交互

- 三栏构筑信息架构、清晰的牌组完成度、预设入口、法力曲线和阵营统计。
- 可读的战场：轮次/阶段、英雄生命/法力、三排关系、战术、速度与日志层级明确。
- 三套同构主题：`default` 深色烫金、`skeuo` 皮革拟物、`pixel` 像素 RPG；主题只改表现，不改规则。
- 首轮轻量新手引导与按需规则说明，不强制老玩家重复观看。
- 桌面与约 390px 窄屏布局；`focus-visible`、可访问名称、键盘主流程、`prefers-reduced-motion` 支持。

### 3.3 保留能力

本次不是删功能重写。以下既有入口和数据契约必须继续工作：组牌、预设/随机牌组、人机、同机热座、PeerJS 联机与观战、Roguelike、收藏与卡包、3D 集卡册、卡牌编辑器、3D 检视、音效、卡牌详情与规则说明。

## 4. 关键设计取舍

### 4.1 加“每轮一个决定”，不加逐单位指令

**选择**：三选一全体增益。

**理由**：部署—布阵—选指令—观看结果形成完整闭环；玩家每一轮都能表达抢血、守场或赌士气，而不必逐个指定攻击目标。

**代价**：战术是方向性修正，不是精确解场；近战随机目标与士气概率仍是游戏的一部分。集火、逐个控制速度属于候选功能，不在本次混进来。

### 4.2 保留自动战斗，优先提升可解释性

**选择**：不改三排遮挡、有效护甲、反击与士气核心结算，新增摘要与状态解释。

**理由**：本作的差异点是阵型与自动演算，而不是传统回合制指向攻击。先让玩家看懂，再决定是否改规则。

**代价**：旧规则仍有学习成本；文档、详情和引导必须共同承担教学，不能只靠一条长规则面板。

### 4.3 速度是表现参数，不是难度或倍率外挂

**选择**：所有结算仍走同一个引擎，只有表现等待随倍率缩放。

**理由**：2x/4x 应减少重复观看成本，不能成为改变胜负的隐藏因素。

**验收方法**：相同牌组与注入的随机序列下，三种速度的英雄生命、阵亡名单、行动/抽牌结果一致。

### 4.4 三主题共用组件，不做三份页面

**选择**：同一 DOM、同一交互状态，由 `data-theme` 和设计令牌改变材质、字形与边界语言。

**理由**：避免功能只在一个主题可用，也避免响应式与无障碍修三遍。

**约束**：主题不得改变卡牌数值、命中区域、DOM 顺序、信息含义；像素主题的硬阴影和拟物主题的纹理都不能降低正文对比度。

### 4.5 零构建优先于框架化

**选择**：继续 plain script、共享全局词法作用域、静态托管；不引入 npm 运行依赖或打包器。

**理由**：当前项目可双击运行、部署简单，重构目标是产品与代码可维护性，不是技术栈替换。

**约束**：新功能必须显式检查脚本加载顺序和跨模块消费者；不能因为“现代”就私自引入模块系统。

### 4.6 收藏经济不在本次重做

**选择**：保留首次全卡收藏与金币/卡包用途，遗物只影响当前远征，不成为永久战力付费墙。

**理由**：本次先解决单局决策与远征构筑，非强度收藏消费需要独立经济设计。

## 5. 验收标准

以下均为可执行验收，不以“看起来现代”作为完成标准。

### 5.1 首轮与构筑

1. 清空牌组后，界面显示 `0 / 60` 与“还差 20 张”，开战不可用且原因可读。
2. 选择一个阵营预设，牌组成为 20–60 张的合法牌组；法力曲线、阵营统计和列表同步刷新。
3. 搜索卡名或描述关键词、按阵营/费用/类型筛选、撤销筛选后结果正确；添加/移除卡牌不丢失搜索输入焦点。
4. 首次用户能按引导完成“预设 → 开战 → 出牌 → 守备 → 指令 → 开始战斗”；再次进入不强制重复引导。
5. 原有人机、热座、联机组牌与提交牌组路径均无回归。

### 5.2 战术、速度与摘要

1. 部署期依次选择猛攻/坚守/集结，可替换选择；进入战斗后不能修改。默认不选时没有战术增益。
2. 构造已知三围单位：猛攻使本轮攻击/反击计算使用的攻击 +1；坚守使本轮有效护甲 +1；集结使本轮士气 +2且仍受 -10～+10 与士气免疫规则约束。
3. 下一轮开始时本轮战术修饰消失；单位详情和日志不会把它写成永久基础增益。
4. AI 至少在进攻、承压、士气可利用的三类局势下会作出有依据的选择；AI 决策输入不包含玩家手牌/牌库顺序。
5. 热座双方和联机双方都只能修改自己的指令；观战者只读；guest 的指令由房主校验并进入快照。
6. 在 1x/2x/4x 下重放同一受控场景，最终结果与详细结算一致，仅等待时间不同；非法倍率不被接受。
7. 紧凑摘要中的双方英雄伤害、阵亡数和结果与该轮详细日志一致；当前战术徽标可确认当轮战术，详细日志可确认具体阵亡名单、战术触发和其他关键结果。`state.roundSummary` 的结构化字段供状态/探针验证，不作为 UI 全字段直显的验收依据；下一轮换摘要，不无限累积。

### 5.3 Roguelike

1. 遗物图鉴至少 6 项，每项都能通过引擎探针观察到与文案一致的效果，而非只显示名称。
2. 精英、中 Boss、最终 Boss 的奖励流程符合实现约定；三选一不重复，选择后只获得一件，不能重复点击套利。
3. 遗物在后续节点生效，地图能查看当前遗物与解释；普通战斗、 campfire、商店、事件流程不回归。
4. 保存并刷新后，地图、路径、生命、牌组、金币与遗物恢复一致；没有 `relics` 的旧档按空列表迁移，不崩溃。
5. 放弃/通关/失败清理的是本次远征，不误删永久收藏；纪念卡与通关奖励仍按既有规则执行。

### 5.4 视觉、响应式与无障碍

1. 三主题分别检查构筑、战场、卡牌详情、卡包、集卡册、编辑器、Roguelike；无文字消失、控件遮挡或不可读组合。
2. 在 1440×900、1024×768、390×844 检查：页面无意外横向滚动，主操作可触达，三排与手牌可辨认。
3. 仅键盘完成核心首轮；焦点始终可见，浮层打开后焦点不丢失，Esc 可关闭允许取消的浮层。
4. 图标按钮有中文可访问名称，战术和速度用单选/按钮状态表达当前值，不只靠颜色。
5. 系统开启“减少动态效果”后，非必要位移、脉冲、翻牌和 3D 装饰被移除或简化；规则与等待结果不变。

### 5.5 工程与发布

1. `node tools/sync-cards.js` 校验通过；`cards.json` 与 `index.html#cards-json` 内容一致。
2. 所有 plain script 通过 `node --check`；主内联脚本按项目既有方式检查。
3. 浏览器控制台无新增异常；实际点击完成“构筑 → 战斗 → 下一轮 → 结算”。
4. 本地 HTTP 预览后验证 3D 检视与 importmap；`file://` 主游戏仍可玩，3D 的网络限制有明确说明。
5. GitHub Pages 发布只提交源码和静态资源，不包含临时探针、日志、缓存或工作区协议文件。

## 6. 成功指标与测量方式

本版本没有新增遥测、账号或在线分析。指标用于本地可用性测试与仿真，不宣称已有线上数据。详细公式见[玩法设计](玩法设计.md#13-平衡原则与成功指标)。

| 目标 | 首轮验收指标 | 样本与工具 |
| --- | --- | --- |
| 快速上手 | ≥80% 首次测试者在 30 秒内借助预设进入首场战斗；≥80% 在首轮结束前完成一次有效战术选择 | 至少 5 名未玩过本作的测试者，记录点击与耗时 |
| 战术有意义 | 三种指令在测试对局均有使用；没有单一指令占全部选择 >70%，或能用数据说明环境原因 | 至少 100 局带指令仿真 + 10 局人工对局 |
| 战斗可读 | ≥80% 测试者能根据紧凑摘要回答双方伤害、阵亡数和结果，在当前战术徽标与详细日志中确认战术，并在详细日志中确认具体名单与关键结果 | 首轮后提问；答案不得只来自 `title` |
| 窄屏可用 | 390px 核心流程任务完成率 100%，无阻断性横向溢出 | 桌面/移动设备或浏览器设备仿真各跑一遍 |
| 构筑有差异 | 至少 6 种遗物均有效；同一阵营不同遗物路线的关键资源/战术选择出现可解释差异 | 遗物定向场景 + 至少 20 次远征奖励流程 |
| 性能可接受 | 常规 20–30 张牌组对局无持续卡顿；4x 不积压失控定时器 | 浏览器 Performance/Memory，连续 10 轮以上 |

阈值是下一轮迭代判据，不是已经达成的实验结论。未达标先记录场景、期望与实际，再决定调 UI、AI 权重或数值。

## 7. 候选路线图（全部未实现）

### P0：先验证本次闭环，再扩规则

| 候选 | 价值 | 前置实验/约束 | 不在本次交付的含义 |
| --- | --- | --- | --- |
| 可复现种子与轻量回放 | 让速度/平衡/bug 能精确复盘 | 统一随机数入口，记录种子和动作序列；联机隐私不能泄露 | 当前没有种子 UI、导出回放或完整录像 |
| 新引导完成度与本地战绩 | 判断玩家在哪一步流失 | 只存本地、提供清除；不默认上传 | 当前没有完整战绩面板或云端分析 |
| 战术平衡第二轮 | 防止某指令成为万能解 | 按阵营、轮次、场面统计选取率与胜率 | 当前只承诺三种指令与基础 AI，不承诺长期 meta 已完成 |

### P1：增加决策深度

| 候选 | 设计方向 | 必须先解决 |
| --- | --- | --- |
| 每轮一次集火标记 | 在自动战斗中提供一个精确目标偏好 | 与三排遮挡、远程启发式、战术预览和多人协议统一 |
| AI 三档风格/难度 | 快攻、控制、组合技，而不是简单加数值 | 建立相同信息集和固定种子对照，避免“难度=偷看手牌” |
| 开局手牌调度 | 降低高费沉底与极端起手 | 同步人机/热座/联机阶段与随机序列，重新评估先后手 |
| 远征进阶难度 | 用规则修饰提高复玩，不单纯堆血 | 先验证遗物池没有永久循环和必胜组合 |

### P2：内容与长期目标

| 候选 | 设计方向 | 边界 |
| --- | --- | --- |
| 非强度收藏消费 | 卡背、异画、头像、纯展示闪卡 | 不削弱首次全卡可构筑的友好性，不引入付费 |
| 每日种子/挑战 | 同条件牌组或远征排行榜 | 需要可复现种子与防作弊边界；当前无服务器排行 |
| 阵营英雄扩展 | 强化 13 阵营身份与技能构筑 | 新机制走 cards.json/词条/AI/评分完整注册流程 |
| 战绩、MVP 与结算分析 | 给对局留下可理解的结果 | 先有结构化事件，不能从中文日志反向猜统计 |

### P3：仅在收益明确时考虑

- 反击射程模型简化、行动速度公式重做、守备墙上限等基础规则改写。
- 服务端权威房、断线重连、跨设备收藏同步。
- 组件框架或构建链迁移。只有纯静态全局脚本的维护成本已被实际数据证明高于迁移成本时才立项。

这些项目均为**候选（未实现）**；不得因出现在本文或旧《平衡性评审》中，就在 README、卡面文案或发布说明中写成已有能力。

## 8. 文档维护规则
