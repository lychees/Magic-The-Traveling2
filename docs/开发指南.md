# 开发指南：零构建卡牌游戏架构与交付

> 本文对应当前 plain-script 架构和本次现代化功能。规则数值见[玩法设计](玩法设计.md)，界面契约见[视觉与交互设计](视觉与交互设计.md)，发布范围见[现代化重构](现代化重构.md)。修改本文列出的状态、API、存储键或脚本顺序时，必须同步本文与 `AGENTS.md`。

## 1. 技术约束

- 零构建、零 npm 运行依赖、纯静态托管；主游戏可直接通过 `file://` 打开。
- `index.html` 提供 DOM、`#cards-json` 内嵌数据、启动脚本、`VIEWER_TEXT` 和 holo ES module；`js/*.js` 全是普通 script，不是 ES module。
- 普通脚本共享全局词法作用域：加载顺序就是依赖契约；同名 `const/let` 会重声明，后定义函数会覆盖先定义函数。
- 唯一评分公式是 UMD 文件 `tools/rating.js`，浏览器暴露 `MTCG_RATING`，Node 使用 `require`。
- 联机使用 PeerJS 1.5.4 CDN；3D 使用仓库内 `vendor/three/0.180.0` 和 importmap。3D 模块需要 HTTP 环境，不能把 `file://` 可玩主游戏误解为 `file://` 可运行所有 3D 功能。
- 本次新增战术、速度、遗物、响应式和无障碍也不能引入框架、打包器或新的运行时依赖。

## 2. 本地运行与常用命令

```bash
# 主游戏与 holo 的完整本地预览；项目约定固定 8474
python3 -m http.server 8474 --bind 127.0.0.1
# 打开 http://127.0.0.1:8474/

# 改卡后：校验 cards.json 并注入 index.html#cards-json
node tools/sync-cards.js

# 只有明确要按 tools/rating.js 重算全部评分时才加 --recompute
node tools/sync-cards.js --recompute

# plain script 语法检查
for f in js/*.js tools/*.js; do node --check "$f" || exit 1; done

# 主内联脚本语法检查（沿用项目既有提取方式）
mkdir -p .tmp-test
sed -n '/^<script>$/,/^<\/script>$/p' index.html | sed '1d;$d' > .tmp-test/game.js
node --check .tmp-test/game.js

# 阵营默认卡组仿真；局数可按机器性能调整
node tools/simulate.js 20
```

`.tmp-test/` 是本机测试目录，不是交付源码；不得把生成的 `game.js`、探针输出或截图提交。Python Playwright 脚本只有在本机已经存在时才可运行，标准步骤是先起 8474 服务，再执行对应脚本；仓库不假设所有克隆都自带这些脚本。

### 3.1 普通脚本加载顺序

`index.html` 中的顺序不得随意调整：

```text
#cards-json
  → tools/rating.js
  → js/core-data.js
  → js/net.js
  → js/economy.js
  → js/engine.js
  → js/render.js
  → js/roguelike.js
  → js/card-editor.js
  → 内联启动 / __api
  → VIEWER_TEXT
  → type=module 的 holo
```

关键原因：

- `core-data.js` 先解析 `CARD_DEFS`、常量与存储；依赖 `storage` 的读取必须发生在其初始化之后。
- `net.js` 声明全局 `uid/state/logLines` 和 `NET`，引擎与渲染都消费它们。
- `engine.js` 使用 `NET/RUN` 接口；`RUN` 的 `let` 在 `roguelike.js` 声明，但引擎函数只在后续运行时被调用。不要提前执行依赖 RUN 的顶层逻辑。
- `render.js` 同时消费引擎、经济和 DOM；`roguelike.js` 复用 `render/initGame/showGame`。
- holo 是独立 ES module，通过 `window.__holo`、`window.__drawCardFace`、`window.VIEWER_TEXT` 与普通脚本交互；不要在 `window.__holo = {...}` 初始化之前赋值其方法。

### 3.2 启动与数据流

```text
cards.json
  └─ node tools/sync-cards.js：校验并序列化
      └─ index.html <script type="application/json" id="cards-json">
          └─ loadCardData()
              └─ CARD_DATA / CARD_DEFS / RACES / SCHOOL_INFO / GREEN_DRAGON
                  ├─ 组牌、预设、编辑器、3D 卡面
                  ├─ makeMinion / playSpellCard / AI
                  └─ tools/simulate.js 的同一引擎
```

启动脚本依次应用主题、读取经济、显示构筑、更新静音按钮并暴露 `__api`。holo 完成后再覆盖/补充卡面生成能力；卡面 URL 缓存失败时不缓存空结果，允许模块就绪后重试。

## 4. 运行时状态

### 4.1 对局 `state`

`initGame` 重建普通对局状态，关键结构如下：

```js
state = {
  player: SideState,
  enemy: SideState,
  phase: 'deploy' | 'combat',
  round: 0,                 // startRound 后从 1 开始
  gameOver: false,
  mode: 'ai' | 'pvp',
  deploySide: 'player' | 'enemy',
  tactics: { player: null, enemy: null },
  battleSpeed: 1,
  roundSummary: null,
  _tacticsActive: false,
  _runBattle: false,       // 仅 startNodeBattle 通过 initGame(..., true) 建立
  _relicState: { phoenixFeatherUsed: false },
  anims: { attacker: null, shaken: [], heroHit: null, dying: [] },
  moraleFx: null,
}
```

`SideState`：

```js
{
  hp, maxHp,
  maxMana, mana, burned,
  fatigue,
  deck: [CardDef],
  hand: [CardDef],
  board: [Minion],
  graveyard: [Minion | SpellGraveEntry],
}
```

单位的核心字段：`uid/name/cost/race`、`atk/baseAtk`、`arm/baseArm`、`maxHp/baseMaxHp/curHp`、`traits`、`row`、`defense/grounded/faceDown`、`morale`、`canAttack/counterLeft`、单位法术法力、`playedRound/costPaid/recallable`。前/中/后/空中分别是 `row=0/1/2/3`。

派生约定：

- `baseAtk/baseArm/baseMaxHp` 与永久卡牌增益不是同一种“临时 UI 值”；`recalcAuras` 从基础值和当前光环/战术/遗物重算 `m.atk`。
- `effArmor(m)` 是有效护甲唯一入口，包含姿态/词条/相邻光环、当轮坚守和远征磐石徽记。
- `m._tacticRally` 只记录本轮集结实际增加量，收尾按该值撤回；`state._tacticsActive` 决定猛攻/坚守是否参与计算。
- `state._relicState` 是每场节点战重置的临时计数，不写入永久 RUN。

### 4.2 构筑与界面状态

- `builderSel` / `builderSel2`：`{卡名: 数量}`，分别保存玩家 1 与玩家 2 的选择。
- `curSel`：指向当前编辑对象，不复制牌组。
- `builderMode`：`ai / pvp / net`；`builderStep`：热座当前组牌玩家。
- `builderKw`、`builderFilter`、`builderSort`：卡库搜索/筛选/排序，只影响展示，不改 `CARD_DEFS`。
- `pendingClick`：220ms 单击动作；双击/Shift+Enter 详情要取消对应单击，避免“看详情却出牌/收回”。
- `tacPreview`、各种浮层状态属于表现层，不能成为战斗权威数据。

### 4.3 远征 `RUN`

核心持久字段：`active/race/deck/floor/map/edges/path/curNode/hp/maxHp/kills/rounds/modifier`。新增：

```js
RUN.relics = []              // 已拥有 RUN_RELICS ID，去重
RUN._relicDraft = null       // 待三选一的 ID 数组或 null
RUN._afterRelic = null       // 'draft' | 'victory'
RUN._panel = 'map'           // 当前界面；relic 用于恢复待选奖励
RUN.inBattle = false
```

`RUN_RELICS` 在 `core-data.js` 定义 ID → `{name,desc}`。只有 `startNodeBattle` 通过 `initGame(...,true)` 建立 `state._runBattle`；`inRunBattle()` 统一返回 `state._runBattle && RUN.active && RUN.inBattle`，用于遗物、Boss 和 `roguelikeBattleEnd` 分流。`runRelicActive(key, side)` 还要求 `side==='player'` 且 ID 已拥有。普通 `initGame` 的 `_runBattle=false`，即使 `RUN.inBattle` 残留也不会触发远征效果。

## 5. 函数 API 与事件模型

### 5.1 没有事件总线

项目不使用 EventEmitter 或框架 store。数据变化通过直接函数调用完成：

- DOM 用事件委托：`data-action`（主界面）、`data-rl`（远征）、`data-ce`（编辑器）。
- 原生事件：`click/dblclick/input/change/keydown/dragstart/drop` 等。
- 状态变化后调用对应 `render*()`；`render()` 还会触发房主 `netBroadcast()`。
- `playCard()`、`moveMinion()` 等引擎函数不保证自动重绘。探针直接调用后必须 `render()`；真实点击处理器已有自己的补绘路径。
- `setTimeout` 驱动 `combatTick` 与表现清理；战斗规则不得依赖 CSS `animationend` 才继续。

### 5.2 战术 API

```js
setTactic(side, key) // UI/探针只用两参；side: 'player'|'enemy'；key: 'assault'|'guard'|'rally'|null
setBattleSpeed(n)    // n: 1|2|4
battleDelay(ms)      // 按 state.battleSpeed 缩放表现等待
chooseAITactic()     // 只根据 AI 自己及公开场面评分
```

`setTactic` 必须满足：对局存在、部署阶段、未结束、非观战、side/key 合法、当前身份有权限。人机只能由公开玩家入口设置 `player`；热座只能设置 `deploySide`；host 本地 UI 只能设置 `player`；guest 只能发送自己的 `enemy` 指令。

内部签名还有第三参 `fromGuest`，仅供 `hostHandleAct` 在已校验 guest 消息后以 `setTactic('enemy',key,true)` 代执行。UI/普通探针不得用它越权；guest 调用返回 `true` 表示“动作已发送”，不是“房主已接受”，最终状态等待权威快照，拒绝会走 `actReject`。

规则文案在 `TACTIC_INFO`（`name/desc`）；M1 的界面私有简表是 `UI_TACTICS`（`label/effect`）。二者不能声明同名全局常量，数值/文案修改时必须一起检查。

### 5.3 战术精确流水线

```text
startRound
  → 幂等调用 finishRoundSummary（完成上一轮，不重复结算）
  → state.tactics 重置为 null/null
  → beginRoundSummary（部署开始即创建，记录 startingHp，部署伤害/死亡开始累计）
  → 部署动作与 setTactic
  → startCombat：AI 出牌/施法/守备
  → activateTactics
      ├─ AI chooseAITactic
      ├─ _tacticsActive = true
      ├─ beginRoundSummary（已有摘要，仅更新实际 tactics，保留部署数据）
      ├─ assault/guard 由 recalcAuras/effArmor 派生
      └─ rally 逐单位 changeMorale(+2)，记录 _tacticRally
  → 鼓舞/威吓
  → 重置反击/额外行动/影遁
  → combatTick …
  → finishRoundSummary（轮末或致死才完成）
      ├─ 撤回集结实际值，_tacticsActive=false，recalcAuras
      ├─ 写 endingHp/outcome/completed
      └─ 输出轮次总结日志
  → 下一次 startRound
```

如果 AI 部署期间已造成游戏结束，`startCombat` 不再激活战术或启动下一轮 tick。

### 5.4 轮次摘要 API

```js
state.roundSummary = {
  round,
  tactics: { player, enemy },
  heroDamage: { player: 0, enemy: 0 },
  unitsLost: { player: [{ uid, name }], enemy: [] },
  startingHp: { player, enemy },
  endingHp: { player, enemy },
  outcome: 'ongoing' | 'player' | 'enemy' | 'draw',
  completed: false,
  keyResults: [],
}
```

- `beginRoundSummary()` 在每次 `startRound` 部署开始即创建，记录 `startingHp`；当前轮已有未完成摘要时只更新 tactics，因此 `startCombat` 不重建对象且保留部署伤害/名单。`currentRoundSummary()` 只接受当前轮且未完成的对象，轮末或致死才 `completed=true`。`startNodeBattle` 覆盖继承/Boss 生命后同步双方 `startingHp/endingHp`。
- `damageHero(side, amount)` 是英雄伤害及摘要计数的共同入口，包括直接攻击、疲劳和相应法术效果；新效果不得绕过它另写 `hp -=` 而不记摘要。
- `unitsLost` 在死亡清理记录；凤凰之羽挽救的单位不能同时计为阵亡。
- `recordRoundKey(text)` 记录关键结果并限制为最新 16 条；`finishRoundSummary(outcome)` 只完成一次当前摘要。
- `outcome` 的 `player/enemy` 是 side，不是“当前屏幕下方/上方”；UI 必须经 `sideName/viewSide` 转换。
- 详细 `logLines` 继续保留，最多 60 行；摘要不能靠解析中文日志补生成。
- 上述字段是状态/探针契约，不是 UI 全字段直显承诺。紧凑 UI 只显示双方英雄伤害、阵亡数和结果；当前战术徽标确认战术，详细日志确认具体名单与关键结果，`title` 不能成为键盘或触屏唯一入口。

### 5.5 调试接口

主内联脚本暴露 `window.__api`，包括：

- 对局：`initGame/getState/playCard/doAttack/startCombat/startRound/nextActor/autoAttack`。
- 规则：`effCost/effArmor/canTarget/legalMinionTargets/canHitHero/canCounter/meleeTargets/exposure/speedOf/unitPower/attackDamage`。
- 部署：`moveMinion/recallMinion/castUnitSpell/toggleDefense/toggleLand/flipUnit/aiCastSpells/aiSetDefense`。
- 构筑：`builderSel/builderSel2/deckFrom/selectedDeck/PRESET_DECKS/applyPresetDeck/renderBuilder/deckStats`。
- 联机：`NET/hostHandleData/clientHandleData/makeSnapshot/applySnapshot/netBroadcast/netLeave`。
- 经济与远征：`getGold/getCollection/storage/getRUN/startRun/startNodeBattle/roguelikeBattleEnd/clearRun`。

本次新增的 `setTactic/setBattleSpeed/chooseAITactic` 是普通脚本共享的全局词法函数，可在浏览器控制台或 Node vm 中直接调用；不要假设它们一定被重新导出为 `window.__api` 属性。若以后加入 `__api` 导出，需同步此清单，探针仍应调用真实实现而不是复制一份。

`window.__holo` 提供 `open/openAlbum/openPack/openBox/close`；`window.__drawCardFace` 供 2D 卡面缓存与编辑器使用；`window.VIEWER_TEXT` 是 holo/编辑器描述表。

## 6. `cards.json` 同步铁律

1. **只编辑 `cards.json`**，绝不手改 `index.html#cards-json`。
2. 执行 `node tools/sync-cards.js`。工具先全量校验，任何错误都会非 0 退出且不修改 HTML。
3. 校验覆盖：根结构/version/races/schools/tokens/cards、唯一 name、合法 race/target、有限数值、traits/actSpells/art 结构等。
4. 同步后同时提交 `cards.json` 与 `index.html`，运行时使用内嵌块而非 fetch 外部 JSON，因此只提交其中一个会线上不一致。
5. `rating` 不另写公式。确需重算全部评分才用 `--recompute`；新词条先改 `tools/rating.js` 的 `traitW`，再评估是否重算。
6. 绿龙 token 必须在 `tokens` 中；普通卡名是唯一键，重命名涉及收藏、预设、覆盖层和存档迁移，不能当普通文本替换。

新增只有既有机制组合的单位卡通常只需数据 + sync；新机制不是“加一条 JSON 就完成”。

## 7. localStorage 与迁移

### 7.1 键清单

| Key | 类型/内容 | 生命周期 |
| --- | --- | --- |
| `mtcg-collection` | JSON `{卡名: 拥有数}` | 永久收藏 |
| `mtcg-gold` | 十进制数字符串 | 永久金币 |
| `mtcg-econ-v2` | `'1'` | 全卡收藏迁移标记 |
| `mtcg-albums` | JSON `{阵营: true}` | 每阵营传说奖励领取 |
| `mtcg-run` | JSON `RUN` | 当前远征；含遗物与待选奖励 |
| `mtcg-memorials` | JSON 数组，最多保留 30 个 | 失败纪念卡 |
| `mtcg-config` | JSON `{heroHp,maxMana,allowSet,allowDefense}` | 对局规则配置 |
| `mtcg-card-overrides` | JSON `{原名: def}` | 内置卡覆盖层 |
| `mtcg-custom-cards` | JSON `[def]` | 自定义卡 |
| `mtcg-theme` | `default/skeuo/pixel` | 主题 |
| `mtcg-guide-v1` | JSON `{builderDone,battleDone}` | 两段新手引导 |
| `mtcg-dev` | `'1'/'0'` | 开发者模式 |
| `sfx-muted` | `'1'/'0'` | 音效静音 |

普通对局 `state`、战术选择、战斗速度和构筑筛选不是完整存档；不要声称刷新能恢复普通对局。远征才通过 `mtcg-run` 恢复。

### 7.2 存储兜底

`core-data.js` 的 `storage` 包装先测试 localStorage 可用性；不可用时退化为页面生命周期内的内存对象。读写仍需 `try/catch`，因为隐私模式、配额和 JSON 损坏都可能失败。`sfx-muted` 目前直接使用原生 localStorage，也必须保持自己的异常保护。

存储不可用不能阻断游戏，但应告知“关闭后可能丢失”；不要把内存兜底误写为已经云端同步。

### 7.3 迁移规则

- 每个键独立解析和校验，不因一个坏键清空全部站点数据。
- 缺字段用默认值补；数值必须 `Number.isFinite`，数组/对象先验形，ID 必须存在于当前定义表。
- 写新字段前保留旧字段；只有确认新结构完整后才更新版本标记。
- 经济旧档通过 `mtcg-econ-v2` 补齐全卡收藏；之后出现的新卡只补发缺失项，不覆盖玩家已有数量。
- 远征旧档没有 `relics` 时补 `[]`；拥有 ID 过滤无效项并去重。`_relicDraft` 只保留未拥有且有效的至多 3 个 ID；无效候选连同 `_afterRelic` 清空，避免恢复到无法领取的页面。
- 名称是收藏和卡牌覆盖的稳定键。卡名变更必须显式迁移，不自动模糊匹配。
- 大改前建议通过编辑器导出/复制相关键备份；禁止用 `localStorage.clear()` 作为迁移手段。

## 8. 多人权威状态与隐私

### 8.1 拓扑

```text
guest ── action ──→ host（完整 state + 规则校验）
                      ├─ makeSnapshot('enemy') → guest
                      └─ makeSnapshot(null)    → spectators
host 本地玩家 = player；guest = enemy；观战只读
```

- 房主执行 `initGame/startRound/startCombat/combatTick`，guest 不运行权威战斗逻辑。
- `render()` 触发 `netBroadcast()`；动作处理器也可兜底广播。
- 断线/房主离开当前只提供结束提示，不等于支持断线重连或服务端存档。

### 8.2 动作协议

已有 `kind`：`play/move/recall/cast/land/defense/flip/set/endDeploy`。本次增加：

```js
{ t:'act', kind:'tactic', key:'assault'|'guard'|'rally'|null }
{ t:'act', kind:'battleSpeed', value:1|2|4 }
```

`tactic` 仍受部署阶段与 `deploySide==='enemy'` 校验；`battleSpeed` 是表现参数，由 host 接受后写入状态并广播，不改变任何规则。非法动作返回 `actReject`，客户端不得先伪造成功结果。

### 8.3 快照新增字段

```js
{
  t:'state', phase, round, deploySide, gameOver,
  tactics: {player, enemy},
  tacticsActive: Boolean(state._tacticsActive),
  battleSpeed: 1|2|4,
  roundSummary: state.roundSummary || null,
  sides: { player, enemy },
}
```

`applySnapshot` 重建瘦客户端 `state`，对缺失/非法新字段使用安全默认值。新增字段必须同时检查序列化、快照、应用、观战与旧客户端兼容，不可只改 host。

### 8.4 个性化与打码

- 接收者只能看到自己的 `hand/deck` 卡名；另一方为 `null` + 数量。
- 非接收者视角的盖牌通过 `maskFaceDown` 只保留公开所需信息，不能泄露名称、三围、词条、战吼或手牌。
- 墓地、轮次摘要和 `keyResults` 是公开信息；新增记录前检查是否把未揭示盖牌/私有抽牌写进去。
- 公共日志在双人模式不写具体摸牌名。
- 观战只见公开场面，不得调用动作；所有引擎入口仍需检查 `NET.role==='spectator'` 或身份权限，不能只禁用按钮。

## 9. 远征奖励与存档流程

本次稳定遗物 ID 与引擎挂点如下；改名只改 `RUN_RELICS` 的 `name/desc`，ID 变更则需要存档迁移。

| ID | 引擎挂点 | 每场/持续状态 |
| --- | --- | --- |
| `warDrum` | `recalcAuras`：全队攻击 +1 | 持续派生 |
| `stoneAegis` | `effArmor`：全队有效护甲 +1 | 持续派生 |
| `longBow` | `recalcAuras`：远程攻击 +2 | 持续派生 |
| `spikedShield` | `executeCounter`：反击伤害 +2 | 每次反击 |
| `rallyBanner` | `activateTactics` 后：全军士气 +1 | 每战斗阶段一次 |
| `bloodChalice` | `onAttackKill`：攻击/反击击杀回血 2 | 每次合法击杀 |
| `arcaneTome` | `initGame` 初始 5 张后额外摸 2 | 每场一次 |
| `phoenixFeather` | `cleanupDead` 首个将死单位以 1 血留场 | `_relicState.phoenixFeatherUsed` 每场重置 |

`checkGameOver` 只有 `inRunBattle()` 为真才分流到 `roguelikeBattleEnd`；普通人机/热座/联机即使存在残留 RUN.inBattle，也走普通结算。

```text
roguelikeBattleEnd(won)
  → 写生命/击杀/轮数、发节点金币、RUN.inBattle=false
  → elite/boss/finalBoss：relicDraftChoices()
      ├─ 从未拥有 RUN_RELICS ID 洗牌取至多 3 个
      ├─ 写 _relicDraft + _afterRelic('draft'|'victory')
      └─ saveRun + openRoguelike('relic')
  → relic-pick：再次校验 panel/候选/未拥有
      ├─ relics.push(id)，清候选，saveRun
      ├─ draft：进入原有卡牌三选一
      └─ victory：进入通关奖励
```

- 已拥有遗物不会再次进入候选；同一 ID 不能靠连点重复获取。
- 最终 Boss 的遗物选择发生在通关结算前，不能跳过 `_afterRelic==='victory'` 的恢复。
- 普通战斗没有遗物三选一；遗物池不足时不制造空奖励页。
- `saveRun` 存 ID 而非整份定义/引擎状态；`_relicState.phoenixFeatherUsed` 在每场 `initGame` 重置，不膨胀 RUN。

### 11.3 速度不变性的最小方法

1. 在 `initGame` 前用可复现序列替换 `Math.random`，每个速度档重新加载同一状态/脚本环境。
2. 记录洗牌、部署、行动者、目标、士气、伤害、死亡、英雄生命和最终奖励。
3. 分别以 1/2/4 驱动定时器队列，不依赖真实等待。
4. 深比较规则结果与随机调用次数；允许不同的只有时间戳/等待时长/表现字段。
5. 若不同，先找“在 timeout 回调里才生成随机数”或“速度值进入规则公式”，不要通过重复跑直到碰巧一致。

## 12. 调试

- `window.__api.getState()` 查看权威状态；`window.__api.getRUN()` 查看远征；`NET.role` 确认身份。
- `globalThis.__noRender = true` 可在无头 harness 关闭渲染；注意 `render()` 的广播位于该短路之前，网络测试不要误关广播。
- 直接引擎调用后手动 `render()`；测试结束恢复随机数、计时器、存储与 `__noRender`。
- 排查战术先看：`state.tactics → _tacticsActive → m.atk/effArmor(m) → m._tacticRally → roundSummary.completed`。
- 排查遗物/Boss 上下文先看：`state._runBattle → inRunBattle()（同时含 RUN.active/inBattle）→ RUN.relics/modifier → runRelicActive → state._relicState → 当前节点和 side`；普通 `initGame` 若受残留 RUN 影响，先检查是否错误传入了第四参 `runBattle=true`。
- 排查联机先比较 host 完整 state、guest 个性化快照和 guest apply 后 state，不要在 guest 上运行 `combatTick` 试错。
- 对随机 bug 保存随机序列/动作序列；当前没有完整种子回放 UI，不能把手动注入能力写成玩家功能。

## 13. 性能与稳定性

- 当前渲染大量重建 `innerHTML`，新增组件不要在一个 tick 内重复无意义 `render()`；先改状态，再集中补绘。
- 日志最多 60 行、摘要关键结果最多 16 条；新增历史不得无限增长或塞入每帧快照。
- 手牌上限 10、每方场上限 50 是硬保护；召唤/分裂循环仍要设置触发次数和 guard。
- 卡面通过 `faceCache` 缓存；缓存键是卡名，编辑器改变卡面后要有失效策略，不能展示旧图却以为已更新。
- 4x 只缩短定时器，不在一个 tick 重放多次；切回构筑/新对局时防止旧回调写入新 state。
- 避免把完整 `RUN.deck` 或卡牌定义重复复制到每个单位/快照；遗物存 ID、网络手牌存名称。
- 3D/集卡册是独立重资源场景，关闭时清理不必要的动画/对象；低性能和减少动态环境保留 2D 路径。
- 用 Performance/Memory 实测 10 轮以上长局与 4x；没有 trace 时不宣称“性能提升 X%”。

## 14. 安全与隐私边界

1. **房间密码只是轻量校验**，不是账号认证、加密或防作弊；PeerJS 公共 broker 与 P2P 网络也不保证可达。不要在房间名/密码/昵称中放敏感信息。
2. 房主权威只能防普通客户端误操作，不能防恶意房主，也不是竞技级反作弊。当前没有服务端签名、回放公证或云存档。
3. 个性化快照是隐私核心。新增字段默认视为公开，除非明确加入接收者裁剪；盖牌和手牌绝不能因摘要/调试字段泄露。
4. 外部 CDN PeerJS 是供应链和网络可用性边界；本地模式必须在加载失败时工作。Three.js 使用仓库固定版本，不动态拉 latest。
5. 自定义卡/覆盖层导入、玩家昵称、网络消息都按不可信输入处理。现有界面广泛使用 innerHTML，新增代码必须转义动态文本或使用 textContent，并校验数值/ID/数组长度；不能将导入 JSON 当成可执行 HTML。
6. 不执行导入的 `script` 字段，不用 `eval`；仿真只加载仓库明确列出的脚本。`resolveSpellEffect` 等 key 必须白名单。
7. localStorage 是同源可读数据，不存密码、令牌或个人敏感信息；清站点数据会丢失收藏/远征。
8. 发布前检查无临时刷钱状态、房间密码、调试数据或秘密文件被复制到 `.deploy`。

```bash
cp index.html cards.json README.md PRODUCT.md DESIGN.md AGENTS.md style.css card-viewer.html .deploy/
cp -r js tools docs vendor .deploy/
cd .deploy
git add -A
```
